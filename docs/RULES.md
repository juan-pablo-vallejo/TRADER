# TRADER — Development Rules

How work is done in this repository. What is being built → [PRD.md](PRD.md); how the system is
shaped → [ARCHITECTURE.md](ARCHITECTURE.md). Where a rule here and the code disagree, the code
is wrong.

## Authority

1. [PRD.md](PRD.md), [ARCHITECTURE.md](ARCHITECTURE.md), [DESIGN.md](DESIGN.md) and this file
   state what is decided. [TASKS.md](TASKS.md) states the order. [MEMORY.md](MEMORY.md) states
   what happened. Code conforms to all of them.
2. A decision changes by editing its home so the home is simply correct, and by adding a row to
   the decisions table in ARCHITECTURE.md. An undocumented supersession is a defect.
3. Every fact has exactly one home. Other documents link to it; they never restate it.

| Fact                                                               | Home                                  |
| ------------------------------------------------------------------ | ------------------------------------- |
| Scope, users, features, business rules, pilot and V1 definitions   | `docs/PRD.md`                         |
| Stack, invariants, sync protocol, domain, folder tree, decisions   | `docs/ARCHITECTURE.md`                |
| Principles, coding standards, placement, git, CI, session protocol | `docs/RULES.md`                       |
| Tools, what each may touch, what counts as destructive             | `docs/RULES.md`, Toolbox              |
| Palette, typography, spacing, components, UI localization          | `docs/DESIGN.md`                      |
| Stages, tasks, done-criteria, what is checked off                  | `docs/TASKS.md`                       |
| Session log, context, gotchas, where the archive is                | `docs/MEMORY.md`                      |
| Environment variable contract                                      | `.env.example`                        |
| Versions and tooling                                               | `package.json` files and the lockfile |
| Why one line of code exists                                        | the comment beside it                 |

## General principles

- Correctness and maintainability over speed; boring, stable technology over new; managed
  services over self-run ones; clean foundations over shortcuts.
- Verify before asserting. Versions, prices and platform policy are checked against the
  registry or the vendor's page, not recalled. A claim that cannot be sourced is a defect.
- A test you have not watched fail proves nothing: remove the guard, see red, restore it.
- Reviews are input, not instruction. Check their premises before acting on them.
- Plan first for anything touching schema, auth, sync, money or CI; the plan is what gets
  reviewed. Say what was not done.
- A procedure added to the API gets a line in the gate inventory test
  (`packages/api/test/core/gates.test.ts`) in the same commit; the test fails without it.
- Scope is explicit. A scope change is its own line in TASKS.md, never a by-product of a
  "housekeeping" commit.
- Sequence by dependency. Documents carry no dates or deadlines unless Juan Pablo sets one.
- The sync layer is built with deliberate failure injection — dropped responses, duplicate
  pushes, a two-day backlog, a wrong clock — not happy-path tests.

## Technology and coding standards

- TypeScript everywhere, `strict`. Formatting is whatever `pnpm format` produces; lint is
  `pnpm lint`. Both pass before a commit.
- Cross-package type imports use `import type`; otherwise Metro bundles server code into the
  app, and the lint rule makes that an error.
- Every boundary is validated with zod: procedure inputs, sync payloads, environment variables.
- Money is integer minor units plus a currency code; columns end in `_cents`. Ids are UUIDv7,
  generated by the device that observed the event. Times are UTC timestamps; `work_date` is
  derived in `companies.timezone`.
- Append-only tables have no `updated_at`, no UPDATE path in code, and a trigger that rejects
  one.
- Migrations are additive and reviewed as plans. Every tenant-scoped query runs with
  `app.company_id` set.
- Auth guards fail closed at request time, never by throwing at module load — that breaks
  `next build`. A switched-off route answers 404; an API call answers 401 without an active
  user and 403 when its role is not admitted.
- Three seams stay thin so a vendor can be swapped without a rewrite: the identity adapter, the
  database driver behind an environment variable, the error-reporting wrapper.
- Every crew-facing string goes through the i18n layer with English and Spanish entries; a
  hard-coded string in a crew screen fails review.
- Every control in `apps/mobile` carries a `testID`; a Maestro flow selects by it, never by
  visible text, which is in two languages.
- Secrets never enter the repository. `NEXT_PUBLIC_` and `EXPO_PUBLIC_` mean public, literally.
  The repository is public; machine names and addresses stay in `~/.ssh/config`.
- No new dependency, tool or version bump without a line in TASKS.md naming what consumes it.
  pnpm's minimum-release-age quarantine stays on.
- Inside a package: `src/` code, `test/` tests in folders that mirror `src/`, a `README.md`
  only for a runbook nothing else owns. Invariant tests run against a real Postgres. Tests and
  the seed run only against the local compose database or CI's service container; they refuse
  to start while `DATABASE_URL` is set.
- Every promise is awaited or deliberately discarded with `void`; lint enforces it. A
  statement on a transaction that is never awaited runs after the transaction has ended.

## Project structure

- The root holds only files their tooling requires. Documents live in `docs/`; the set is fixed
  at the six in the authority table plus `CLAUDE.md`, `README.md` and `LICENSE`.
- No line caps. A document is as long as its facts need, and no longer: it states each fact
  once, in its home, and links instead of restating. `CLAUDE.md` stays short because it is
  read in full every session.
- `packages/*` is shared code consumed by `apps/*`; nothing in `packages/` imports from `apps/`.
- Files are kebab-case; React components PascalCase; database tables and columns snake_case;
  foreign keys end in `_id`. One Drizzle schema file per table group under
  `packages/db/src/schema/`.
- Before adding a file, name what consumes it. A file with no consumer is not added.

## Git and CI

- `main` is protected: pull request plus the required check `check`, the literal job name in
  `.github/workflows/ci.yml`. Branch per TASKS line, pull request, `check` green, then
  `gh pr merge --merge --delete-branch`; direct pushes to `main` are refused. The agent
  pushes its feature branch and opens and updates that branch's pull request; the merge is
  Juan Pablo's.
- One logical change per commit. Imperative subject ≤ 72 characters, no trailers of any kind
  (no `Co-Authored-By`), SSH-signed. A body only when the subject cannot carry the why.
- One workflow, one job: install, typecheck, lint, format check, build, migrate, test. Every
  run on `main` completes; only a superseded pull-request run is cancelled.
- Dependabot is off. Dependency updates are tasks, verified against the registry.
- Branches other than `main` are short-lived and deleted on merge. A merge into `main`, a
  force-push and a branch's deletion are human actions in a terminal, never agent actions.

## Toolbox

What a session works with beyond the repository, and where each tool stops. The decision is
ARCHITECTURE's (2026-11-14, staging autonomy); the permission rules and the wrappers live on
the owner's machine, outside the repository.

- **Three environments.** Local: the compose database and `.env`. Staging: a Neon project
  of its own, Clerk's development instance, Vercel previews. Production: the owner's alone.
  A session holds no production credential and runs no production command, read or write.
- **A credential is used, never read.** Each staging secret is an item in the owner's
  macOS Keychain, handed to one fixed command by a wrapper that refuses any other target. A
  session never prints one, never writes one to a file, and never reads `.env` or the
  Keychain itself.
- **Which tool for which job.**

  | Job                                           | Tool                                                                        |
  | --------------------------------------------- | --------------------------------------------------------------------------- |
  | Read staging's data and schema                | Neon's connector (read-only), or `psql` as `trader_app` through its wrapper |
  | Write staging's data as the application would | the deployment itself, or `psql` as `trader_app`                            |
  | Onboard a company on staging                  | the owner-role wrapper's `onboard`                                          |
  | Neon branches and operations                  | the Neon CLI through its wrapper, pinned to the staging project             |
  | Test people at the identity provider          | the Clerk wrapper or CLI, fictional numbers only                            |
  | Deployments, logs, a preview's variables      | Vercel's connector to read; the Vercel CLI to redeploy and to set           |
  | Error reports                                 | Sentry's connector, or the Sentry CLI through its read-only wrapper         |
  | A browser on a deployment                     | the staging browser suite (`pnpm e2e:staging`, `apps/web/e2e`)              |
  | A browser on this machine                     | the Playwright connector against `next dev`                                 |
  | The phone app                                 | Maestro and its connector, on a simulator or an emulator                    |
  | Library and vendor documentation              | the vendor's own connector or page, never memory                            |

- **Routine staging work needs no approval**: reads, SQL as `trader_app`, onboarding, a
  test user, a redeploy, a preview's non-secret variable, a Neon branch created, the
  browser suite.
- **A destructive step is approved one at a time, on staging too**: DROP, TRUNCATE, a
  DELETE or UPDATE without a key, REVOKE, any SQL as the database's owner, a role or
  password change, a Neon restore, reset or deletion, a variable removed, a test user
  deleted, and any cleanup of a fixture, synthetic ones included.
- **A tool is verified before it is relied on**: its version is read from its registry, at
  least a day old; its first use is a read whose answer is already known; a rule that
  should refuse is watched refusing. A tool registered while a session is open answers
  only in the next one.
- **Browser flows live in `apps/web/e2e/`**, apart from `test/`: they need a deployment and
  a secret, so `pnpm check` and CI never run them. A flow sends the bypass to the preview's
  own host alone, records no trace, and deletes nothing.

## Session protocol (Claude Code)

1. Start from `docs/MEMORY.md`, then read `docs/TASKS.md`. Work only the task Juan Pablo
   names, or the next unchecked task in the current stage.
2. Before editing anything under schema, auth, sync, money or CI: write the plan, stop, wait.
3. Make the change; run `pnpm check` (typecheck, lint, format check, tests). Per-commit green
   is `pnpm check` against a database migrated to that commit's own journal; one fully
   migrated database carried across commits is a false red.
4. Commit per the rules above. Push the feature branch and open or update its pull request;
   never push to `main`, never merge.
5. End by ticking the task in TASKS.md and appending an entry to MEMORY.md in its format. Never
   edit PRD, ARCHITECTURE or DESIGN to match code — flag the mismatch instead.
